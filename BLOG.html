Reproduction notes

Agent memory fails at the interface, not the model

Notes from reproducing a write-time memory architecture — and the week the JSON schema turned out to be the bottleneck.

Huy X. Dang · August 2026

We set out to reproduce the architecture from “Better Agent Memory Starts Before Retrieval”: an LLM extractor that writes two kinds of memory records at conversation time — narrative records that preserve reasoning, atomic records that preserve exact facts — into an append-only store where updates supersede rather than overwrite. The thesis of that article is that the highest-leverage optimization happens at write time, when information is extracted into memory, not later when it is searched for.

The thesis survived our attempt to reproduce it — in a way we didn’t expect. The write path was the bottleneck, but the biggest lever inside it wasn’t the extraction model, the retrieval stack, or the prompt alone. It was the interface: the shape of the JSON we forced the extractor to emit.

Retrieval lost nothing. Extraction lost almost everything.

Our first end-to-end runs were bad, and the failure analysis was unambiguous: of 28 bucketed failures on our evaluation slice, 22 were facts that never got extracted. When we later instrumented the store directly, the retrieval number went to zero — across every configuration we measured, no fact that made it into the store failed to surface when its question came.

So we built the tightest loop we could around that one stage: run extraction only, then check whether each benchmark question’s answer exists in the store — no answering model, no judge, about 100 seconds per iteration on a laptop. Most of what follows was found with that loop and confirmed at scale afterward.

The model was not the bottleneck

The obvious suspect was our small local extractor (Qwen3-4B). So we ran the same pipeline with a frontier model, then with an even stronger one. The two frontier tiers produced identical miss sets — capability saturated — and both still left roughly half the needed facts out of the store. When the strongest model you can buy misses half the facts, the problem is what you asked for, not who you asked.

What we were asking for was hostile

Our original extraction contract required, per memory: a type, the content, a list of entity names, and — for updates — the exact ID of the superseded record, copied out of a JSON blob of candidates. Small models botched the transcription constantly: invented IDs, the string "null", mangled copies. Every botch cost the whole record to validation — about 50 good facts rejected per run. The prompt compounded it: be concise, don’t repeat, output an empty list when nothing durable is new. The model obeyed, and saved little.

We changed two things. The contract shrank to two fields plus an optional numbered pointer, with our own code resolving the pointer, deriving entities, stamping dates, and embedding the text. And the prompt flipped from precision to coverage: preserve every explicit fact likely to support a later question; emit separate records for independent facts.

Gate it like you mean it

Cheap loops overfit. Earlier in this project, a single-record-type ablation “beat” the canonical two-type design by 2.2 points on our dev split and briefly got promoted — a difference of one net answer across 56 questions. We reverted it and wrote a rule: architecture-level changes need at least +3 points of macro judge accuracy on the dev split, confirmed on a holdout split the change has never seen.

Formats change what models bother to do

The best finding of the week came from a variant that lost. Mid-redesign, an appealing idea surfaced: drop the numbered pointer too, and let the model express an update by restating the fact it replaces — {"content": "Huy has 4 dogs.", "replaces": "Huy has 5 dogs."} — with the harness matching the restated text back to a stored record. More natural for a language model; self-documenting in the logs. On the fast loop it looked like the winner.

At full-pipeline scale it scored below the old interface. The post-mortem was not what we expected. The text matching was fine — 37 of 45 emitted links resolved correctly. The problem was that there were only 45 links.

Restating a sentence is work, and it carries an implicit accuracy bar — so when unsure, the model wrote null. An unlinked update never demotes its stale predecessor, so every question about a changed fact became a coin flip between the old and new value. A three-character link gets used; an expensive link gets skipped. Emission formats don’t just bound what a model can express — they set the price of each behavior, and models economize.

Never modify, only append

None of the interface work touched the storage semantics, which are the article’s core design and worth seeing concretely. A fact that changes twice is three ordinary rows; each new row names its predecessor, and no row is ever edited:

What didn’t work, so you don’t have to

  • Plain-text output (no JSON). Without a grammar constraint the model rambles; the parser ate its own template echoes. Recall: zero.
  • Letting the model think first. Thinking mode plus JSON-schema enforcement returned empty responses on our local stack.
  • A smaller extractor (1.7B). Perfect JSON, no judgment — recall collapsed to a third of the 4B model’s.
  • Extracting per message instead of per session. Same recall, 14× the calls.
  • A faster serving stack. Prefix caching and speculative decoding on llama.cpp measured slower end-to-end than the boring baseline — local extraction latency is decode token count, and nothing else.
  • Trusting one metric. Strict substring recall scored a store containing “tattoos of her dogs” as a failure against gold “tattoos of her four dogs”. We now run a cheap coverage score in the loop, an LLM judge as arbiter — and, after the restating episode, a link-rate counter, because neither of the first two can see supersession behavior.

Where the reproduction actually stands

Honesty section. The article’s headline result is that memory beats sending the full conversation history — 90.6% vs 60.6% on LongMemEval — with 97% fewer tokens. We are not there:

On our 90-question signal subsample, memory wins one benchmark of three and trails the other two; our token reduction is real but smaller than claimed (~40%, not 97%). We have not yet run the full benchmarks, and our local-model distillation story is unfinished.

What we can confirm from our own data: the write path is where the leverage lives, exactly as the article argues — we moved end-to-end accuracy nine points without touching retrieval or answering. The remaining gap is concentrated in exact-value retention (specific times, URLs, dates that die during extraction), and that is a write-time problem too.

The architecture reproduces. The numbers, so far, don’t — and the distance between those two sentences is where we’re working next.

Everything here is reproducible from the repo: the fast extraction loop, the gated comparisons, per-run checkpoints, and a findings file that includes the negative results. Evaluation slices are stratified subsamples of LongMemEval, LoCoMo, and BEAM; “judged” metrics use an LLM judge over stores or answers as noted.
